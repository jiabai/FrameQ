# Locus v0.6.0 — Local Preparation Only (No GitHub Release)

## Purpose / Big Picture

Make v0.6.0 ready to publish from this machine, without publishing it. The rename to Locus and the
de-branding of machine identifiers landed in `5d312de` / `0a8d377` / `83d50ea`. v0.6.0 is the first
release that carries the new name, so its main content is the rename itself plus the upgrade impact
it creates. The user has v0.6.1 features to build next, so this version is prepared as a **local
baseline**: version bumped, release copy written, gates run, build verified — but no push, no tag,
no GitHub Release, no updater assets, no site deployment.

## Scope

In scope (local only):

1. Bump the six release-version sources from `0.5.1` to `0.6.0`, checked by
   `node scripts/check-release-version.mjs 0.6.0`.
2. Write `docs/releases/v0.6.0.md` (the future GitHub Release body).
3. Prepare the marketing site locally: `LATEST_VERSION`, `RELEASE_NOTES_PATH`, and
   `site/src/content/release-notes/v0.6.0.md`. `site/` is gitignored, so these files stay on disk
   and never enter the commit.
4. Record the version in `TASKS.md` and keep this plan in `active/` with the publish checklist.
5. Run the full gate set and a local `tauri build --no-bundle`.
6. Create one **local** commit. Do not push it.

Out of scope (deliberate):

- `git push origin main`, annotated tag `v0.6.0`, GitHub Release, `latest.json` / `.sig` updater
  assets, three-platform CI, `macos-intel-acceptance.yml` dispatch.
- Marketing site deployment. The locally built `site/dist` now points at `Locus_0.6.0_*` assets
  that do not exist yet; deploying it before the release publishes would break the download page.
- Any migration code for the old data directory. Decision `2026-11-09`: the project has no external
  users, so compatibility code would be dead weight. The impact is documented in the release body.

## Risks and Residual Work Before Publishing

0. **Repository rename.** On 2026-11-10 `jiabai/FrameQ` became `jiabai/Locus`. All in-repo release URLs now use the new name; old-name redirects were verified (releases page, asset direct link, `latest.json?updater=1` all 200). Publish v0.6.0 assets under the new name and update the production server's git remote when convenient.
1. **Asset-name gate will fail by design.** The established pre-publish check compares asset names
   with the previous release after normalising the version. v0.5.1 publishes `FrameQ_0.5.1_*`;
   v0.6.0 publishes `Locus_0.6.0_*`. Treat this as an accepted one-time change, not a defect, and
   update the expected set before running the check.
2. **Updater / signature checks still to do.** `latest.json` must carry the two Windows platform
   keys and both signatures must match the uploaded `.sig` byte-for-byte. Range-check the three
   installer URLs from the deployment server (direct GitHub downloads are blocked on this machine).
3. **Release body.** `desktop-release.yml` does not set notes; run
   `gh release edit v0.6.0 --draft=false --notes-file docs/releases/v0.6.0.md` and read it back.
4. **Site date.** `site/src/content/release-notes/v0.6.0.md` uses `date: "2026-11-10"` as a
   placeholder. Before deploying, set it to the UTC date of GitHub's `publishedAt`.
5. **macOS.** Helper bundle rename, ad-hoc signing and DMG naming cannot be verified on this
   machine; the first hosted macOS run is the real proof. `macos-intel-acceptance.yml` is
   `workflow_dispatch` and must be triggered manually.
6. **User data.** `%LOCALAPPDATA%\com.frameq.desktop` is left untouched. Users upgrading from
   v0.5.1 start with an empty library and may see two shortcuts. The release body and site note say
   so explicitly.
7. **Optional PyTorch runtime.** `CARGO_PKG_VERSION` is part of the component directory and
   download URL, so a version bump invalidates the previously downloaded ~140 MB component.

## Publish Attempt 1 (2026-11-11) — Blocked, Tag Respun

- Tag `v0.6.0` at `6f02de1` triggered `desktop-release.yml` run `42986864296`. The Windows job
  failed in 2 minutes at `Prepare bundled runtime resources` with
  `PythonStandaloneUrl is required. Pass the parameter or set the matching APP_* environment variable.`;
  both macOS jobs were skipped because they depend on the Windows job.
- Root cause: the 2026-11-09 de-branding sweep renamed **GitHub Actions Secret keys** along with
  environment variables. The workflows referenced `secrets.APP_PYTHON_STANDALONE_URL` and friends,
  but the repository secrets are still named `FRAMEQ_*` (`gh secret list`, 9 entries). GitHub never
  exposes existing secret values, so the keys cannot be renamed without re-entering every value.
  All eight release-workflow references and the six acceptance-workflow matrix values resolved to
  empty strings. Regular Script/Server/Native CI never reads these secrets, so only a tag build
  could expose it.
- Fix: keep the neutral `APP_*` **environment variable** names consumed by
  `scripts/build-installer.mjs:32-34`, and map them back to `secrets.FRAMEQ_*`. Added regression
  assertions in `desktop-release-workflow.test.mjs` and
  `macos-intel-acceptance-workflow.test.mjs`, and registered GitHub Actions Secret names as an
  external identity in `docs/design-docs/2026-11-09-neutral-naming-policy.md` so a future naming
  sweep does not repeat this.
- Validation: `node --test scripts/tests/*.test.mjs` 58 passed / 0 failed;
  `validate_agents_docs.py` ERROR and WARN both 0/0; `git diff --check` clean.
- Recovery: delete the local and remote `v0.6.0` tags and re-tag the fixing commit. No GitHub
  Release object existed (the failed run never reached `tauri-action`), so no release deletion,
  asset cleanup, or user-facing retraction was needed.
