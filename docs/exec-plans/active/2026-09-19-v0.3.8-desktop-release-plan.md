# FrameQ v0.3.8 Desktop Release Plan

> This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

## Purpose / Big Picture

Publish the current verified desktop source as v0.3.8 so that **already-installed users** receive an upgraded `yt-dlp` and regain the ability to download YouTube videos. A user on v0.3.7 or older cannot get this from a lockfile change: their installed runtime carries the frozen `yt-dlp 2026.7.4`, and only a new installer replaces it. What a user gets that v0.3.7 did not have: YouTube videos whose media-stream fetch was being rejected with HTTP 403 now download and merge successfully, and Settings > App Updates shows "current version v0.3.8" as a read-only line so the installed version no longer has to be guessed from a filename. Local-first, packaging, privacy, and progress-contract boundaries are unchanged. The user authorized a full desktop release on 2026-09-19.

## Surprises & Discoveries

Evidence: The bundled runtime's dependency source was misread at first. `FRAMEQ_PYTHON_STANDALONE_URL` reads like a pre-baked runtime archive, but `scripts/build-installer.mjs:620-621` only extracts a bare CPython runtime from it and `build-installer.mjs:641-652` installs dependencies afterwards with `uv export --no-dev` plus `pip install -r`. The corrective conclusion is that a dependency upgrade needs a lockfile change and a new release, nothing else — no archive rebuild, no re-upload, no secret rotation. Only a CPython major-version change or a new ffmpeg/Deno asset would require touching those secrets.

Evidence: `uv lock --upgrade-package yt-dlp` rewrote 51 lines, most of which had nothing to do with `yt-dlp`. The local toolchain is uv 0.12.5 while the committed lockfile carries `revision = 3`, and the newer version normalizes dependency-edge markers away when the parent package block is already forked by `resolution-markers` (the edge marker is then exactly the complement and therefore redundant). Real examples: `coloredlogs -> humanfriendly`, `numba -> llvmlite/numpy`, and `cuda-pathfinder`. A `(name, version)` multiset comparison over `[[package]]` blocks is the reliable way to tell normalization apart from a genuine resolution change, and it showed the package set identical at 160 blocks on both sides.

Evidence: `uv sync --dev` was killed with SIGTERM and produced no output on its first invocation in this session, then succeeded unchanged on retry (`+ yt-dlp==2026.8.19`). The same pattern was recorded for the v0.3.7 release, where the project `.venv` had to be rebuilt and a build-backend cleanup was intercepted once. Treat a silent SIGTERM here as environmental and retry before investigating.

Evidence: The pre-existing YouTube subtitle path is rate-limited independently of the `yt-dlp` version. On both the old and new releases, the first attempt with `--write-subs --write-auto-subs --sub-langs zh-Hans,...` fails with `Unable to download video subtitles for 'zh-Hans': HTTP Error 429: Too Many Requests`, and only the worker's drop-subtitles retry reaches the media stream. This is why a fix that only touches the media-stream fetch step is sufficient to restore YouTube downloads, and also why the subtitle attempt still costs a wasted round trip per task.

Evidence: A new `impersonation` warning appears on the subtitle path under yt-dlp 2026.8.19 — `The extractor specified to use impersonation for this download, but no impersonate target is available` — and no EJS remote-component requirement (`--remote-components ejs:github`) surfaced for the tested video. The impersonation warning is benign here because it precedes a failure that already has a fallback, but it is a forward-looking fragility worth watching if a future yt-dlp starts requiring an impersonation target on the media-stream path too.

Evidence: `cargo` is not reachable from this session, so the Rust side of the version-display change cannot be compiled locally. However `.github/workflows/unix-process-supervisor.yml` is path-filtered on `app/src-tauri/**` and runs on `push` to `main`, executing `cargo test --manifest-path app/src-tauri/Cargo.toml` on `macos-latest`. Pushing `main` before tagging therefore produces the Rust compile and test evidence that this session cannot, and sequencing the release that way de-risks the tag.

Evidence: `desktop-release.yml` triggers on `push: tags: v*` while `macos-intel-acceptance.yml` is `workflow_dispatch`-only, so tagging alone builds the three-platform draft without producing the Intel acceptance run. `server-ci.yml` is path-filtered on `server/**`, `deploy/**`, and named docs, so a version bump and a lockfile change do not trigger it.

## Decision Log

Decision: Release as v0.3.8 and ship the `yt-dlp` upgrade together with the read-only current-version display. Rationale: the version display is the only practical way for a user to confirm that the upgraded runtime actually landed in their installed build, so the two changes are complementary rather than merely adjacent; the display reuses an existing command and its value is the compile-time crate version, so it adds no drift risk. Date/Author: 2026-09-19 / User + Alex.

Decision: Fix the dependency problem at the lockfile instead of patching the worker. Rationale: `uv.lock` is the sole authoritative source for what the installer bundles, and `yt-dlp` is invoked as a library module (`sys.executable -m yt_dlp`), so pinning or vendoring a different copy in the worker would create a second source of truth for the same tool. Date/Author: 2026-09-19 / Alex.

Decision: Leave the YouTube failure-classification gap out of this release and keep it as tracked debt. Rationale: 403 and 429 currently fall into the generic `YOUTUBE_DOWNLOAD_FAILED` bucket whose copy tells the user to check their network, which is genuinely misleading, but fixing it spans worker classification, the desktop-worker contract, and three locales. Widening the release would delay the fix that unblocks installed users, which is the whole point of this version. Date/Author: 2026-09-19 / User + Alex.

Decision: Push `main` and wait for the hosted macOS Cargo tests before creating the tag. Rationale: the Rust addition to `updates.rs` cannot be compiled in this session, and the tag triggers a long three-platform build whose failure would waste roughly an hour; `unix-process-supervisor.yml` provides the missing compile evidence cheaply on the release commit. Date/Author: 2026-09-19 / Alex.

Decision: Do not deploy production server or migrate its database as part of this desktop publication. Rationale: this release changes no server source, and the server was already deployed, migrated, and end-to-end verified on 2026-09-19. Date/Author: 2026-09-19 / Alex.
