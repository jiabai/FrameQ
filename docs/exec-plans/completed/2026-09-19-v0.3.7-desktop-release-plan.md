# FrameQ v0.3.7 Desktop Release Plan

> This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

## Purpose / Big Picture

Publish the current verified desktop source as v0.3.7 without changing local-first, packaging, privacy, or progress-contract boundaries. What a user gets that v0.3.6 did not have: a Douyin share-page parse that retries with a randomized 3 to 10 second wait instead of failing the task on the first degradation, a visible progress line while it retries, and an activation-panel title that no longer tells the user the code must come from an administrator. Everything else in the release is documentation and ledger work. The user authorized publishing a new desktop release on 2026-09-19.

## Surprises & Discoveries

Evidence: The release body is not produced by any automation. `desktop-release.yml` never passes `--notes` or a body file, so the draft and the published release both started from `tauri-action`'s generic `FrameQ desktop installer and Tauri updater artifacts.` while the published v0.3.6 body carried the full Chinese notes. The reviewed notes therefore have to be written with `gh release edit v0.3.7 --notes-file docs/releases/v0.3.7.md` as an explicit post-publish step, and the body must be read back and compared against the source file. This is now recorded in `docs/EXECUTION_GATES.md` next to the version-ledger gate.

Evidence: The local worker environment had to be rebuilt before any worker gate could run. The project `.venv` was left behind by the retired `bicho` account, and `uv sync --dev` failed once with `Failed to build antlr4-python3-runtime==4.9.3` because the sandbox's bulk-delete confirmation intercepted the build backend's directory cleanup; the retry (with the deletion escalation approved) completed with `SYNC_EXIT=0` and 186 packages in `site-packages`.

Evidence: `cargo` is not reachable from this session at all. The Rust toolchain recorded in `app/src-tauri/target/.rustc_info.json` lives under the retired `C:\Users\bicho\.rustup` path and `cargo` is absent from the PATH, so the local Rust gate cannot run here and must be covered by the hosted workflows.

Evidence: `desktop-release.yml` triggers on `push: tags: v*` and `macos-intel-acceptance.yml` is `workflow_dispatch`-only, so tagging alone builds the three-platform draft but does not produce the Intel acceptance run; that one has to be dispatched explicitly if it is wanted as release evidence.

Evidence: `server-ci.yml` is path-filtered (`server/**`, `deploy/**`, and named docs). The version bump touches none of those paths, so the release commit itself will not trigger Server CI; the relevant hosted evidence has to come from the most recent run on `main`, which is run `35433721253` (success) at `809314c`. The Unix Process Supervisor workflow is green at `5c9e974` (run `35415250114`), which is the commit that touched `app/src-tauri/src/lib.rs`.

Evidence: Two release-gate commands failed for reasons unrelated to the source. `npm --prefix app run build` cannot empty `app/dist/assets` because the sandbox deletes through `node-safe-delete-shim.cjs`, whose bulk guard rejects a 429-file delete against a threshold of 50; the same guard had earlier blocked `uv sync`'s build-backend cleanup. `node --test scripts/tests/*.test.mjs` reported one failure, `copyDenoFromArchive extracts Deno into resources bin`, because the PATH resolved `tar` to PortableGit's GNU tar 1.35, which reads `C:\...` as a remote host and fails with `Cannot connect to C: resolve failed`; putting `C:\Windows\System32` ahead of PortableGit's `usr/bin` selects the bundled bsdtar 3.8.8 and the same suite passes 50/50.

Evidence: `app/tests/app-input.browser.test.ts` is intermittently flaky and the flake is content-independent. The test `freezes confirmed output language across locale changes and uses the new locale next time` waits on `window.__FRAMEQ_UI_SMOKE__.pending.save_default_generation_preferences?.length === 1`. Four runs of the same file: with the activation copy reverted it failed 1/34 and later passed 34/34 with the identical file content, and with the copy applied it failed 1/34 and later passed 34/34. The same content therefore produces both outcomes, so the copy change is not the cause; the wait is timing-sensitive under CPU contention. A full rerun of `npm --prefix app test` passed 762/762.

## Outcomes & Retrospective

Outcome: v0.3.7 is published as the Latest stable release (https://github.com/jiabai/FrameQ/releases/tag/v0.3.7) with the same five-asset shape as v0.3.6. The release commit is `9a0cd65`, the annotated tag dereferences to it, and Desktop Release run `35434877136` finished green on all three platform jobs. Users on v0.3.6 or older get the Douyin share-page retry (worker-side, so only effective once this build is installed), the retry progress line, and the neutralized activation-panel title.

What went well: the draft-first workflow meant the artifact set could be checked against published v0.3.6 before anything went public, and the signature cross-check between `.sig` and `latest.json` was cheap enough to run every time. The local gate run was clean on the first pass for every suite except the two environmental ones already documented below.

What cost time: the macOS Intel job needed roughly 50 minutes for its Rust build, which is the long pole of the whole run and makes the tag-to-publish interval dominated by a single job. Nothing is broken about that, but it means a release cannot be finished inside one short session.

What was nearly missed: `desktop-release.yml` does not set the release body at all, so the published release initially carried `tauri-action`'s generic placeholder while v0.3.6 carried the full Chinese notes. The published v0.3.6 body had been written by hand at release time, which left the step undocumented. It is now recorded in the release flow so the next release sets the body from `docs/releases/<tag>.md` before considering the publication complete.

Residual risk: `macos-intel-acceptance.yml` is `workflow_dispatch`-only and was therefore not run for this release, the same as v0.3.6; the Intel DMG's acceptance evidence is limited to the packaging job succeeding. No clean-machine Windows or macOS manual acceptance was performed, macOS builds remain ad-hoc signed without notarization, and the retry still emits no distinct diagnostic event, so an exported bundle cannot distinguish a first-attempt success from a retried one. The Douyin retry has no hosted or local end-to-end reproduction against a live degraded share page.
