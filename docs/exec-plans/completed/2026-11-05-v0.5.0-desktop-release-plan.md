## Surprises & Discoveries

- `CARGO_PKG_VERSION` is both the PyTorch runtime component directory (`data_storage_root/runtime/pytorch/<version>`) and its release URL (`releases/download/v<version>/frameq-pytorch-runtime-<target>.zip`). Upgrading to v0.5.0 invalidates the v0.4.3 component, so users on the optional PyTorch model download roughly 140 MB again. The default ONNX model is unaffected. Both release notes record this.
- The site release-notes frontmatter date `2026-11-05` matches the GitHub `publishedAt` UTC date, so no date correction was needed.
- The first Native CI attempt on `6857d97` failed one Windows Worker case, `test_markdown_splitter_advances_past_sentence_separator`, because its spawned process exceeded the four-second `join` budget under runner load (1268 passed / 1 failed). The case passed locally, and `gh run rerun --failed` produced attempt 2 with all four jobs green. The flake is recorded in the technical-debt tracker.
- The remaining `0.4.3` strings are historical ledger entries, the v0.4.3 release notes, the installer filename in release-readiness evidence, third-party lock entries, and an arbitrary non-empty fixture string in `app/src-tauri/src/data_storage_validation.rs` whose validation has no equality assertion against the application version.
- The macOS Intel DMG job is the long tail of the release build; the complete run took about one hour. Job conclusions were confirmed through `gh api .../jobs`, not through the exit status of `gh run watch`.

## Outcomes & Retrospective

FrameQ v0.5.0 is published at https://github.com/jiabai/FrameQ/releases/tag/v0.5.0. The six version sources agree on `0.5.0`; the reviewed release body is live; all eight assets are uploaded; the updater manifest signatures match; the ledger, both plan indexes, and the public site agree with the tag. Product acceptance for commit `ff22538` is documented in `docs/exec-plans/completed/2026-11-05-release-readiness-plan.md`, including the Windows installer replacement, installed default ONNX recognition, and both macOS architectures.

Not run and residual risk: no local macOS device covered graphical interaction, Gatekeeper or permission prompts, or the remaining specialized WebView security canaries. macOS builds are ad-hoc signed without notarization. The internal acceptance packages disabled updater sidecars, so the complete public signed-update path was not exercised end to end. `macos-intel-acceptance.yml` needs a manual dispatch and was not run for this tag. Two active plans still record pending complete native URL-flow acceptance for automatic note titles and the sidebar Home.

## Idempotence and Recovery

Source-controlled edits remain reversible with file edits. Do not delete or re-tag an existing public release. If a future hosted release build fails before publication, fix the source on `main`, delete the draft release and the tag, then tag the corrected commit. Site deployments have a timestamped remote webroot backup.
