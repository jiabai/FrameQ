# FrameQ 自助邮件激活码产品规格

## 背景

当前桌面端授权流程要求管理员先在 Admin Web 创建一次性激活码，再通过人工渠道交给用户。用户登录桌面端后，在“账号与授权”页面填写激活码，兑换 31 天处理权益和 20 次 AI Credits。

新的默认流程取消逐次人工发码：已登录但未授权或授权已过期的用户，可以在“账号与授权”页面请求激活码。服务端把一个仅绑定该账号的激活码发送到登录邮箱，用户仍需把邮件中的激活码填回桌面端完成兑换。

管理员创建的通用激活码继续保留，作为运营、支持和补偿以外的独立发放渠道；本规格不改变其现有兑换语义。

## 目标

- 未授权或授权已过期的桌面用户可以自行请求邮件激活码，无需管理员逐次参与。
- 自助激活码只能由申请账号兑换。
- 用户每次权益过期后都可以再次申领，因此可以按 31 天周期无限免费续期。
- 有效授权期间不显示申领按钮，服务端也拒绝申领和自助码叠加兑换。
- 继续复用现有 31 天权益、20 次 AI Credits、邮件 SMTP、hash-only 激活码存储和原子兑换边界。
- 保持管理员通用激活码、Admin Web 和现有桌面兑换入口可用。

## 用户可见要求

- 未登录时不显示申领激活码按钮，只显示现有登录入口。
- 已登录且从未激活，或现有权益到期时，显示“发送激活码到邮箱”按钮、激活码输入框和兑换按钮。
- 有效权益期间隐藏申领按钮；成功兑换后立即刷新账号状态并隐藏该按钮。
- 点击申领按钮后，界面显示发送中状态，避免重复提交。
- 服务端接受邮件后显示明确成功提示，并在冷却期内禁用再次发送；激活码输入框保持可用。
- 邮件说明绑定邮箱、兑换截止时间、31 天权益和 20 次 AI Credits，并提醒不要转发。
- 用户手动填写邮件中的激活码并兑换；客户端不自动读取邮箱、不自动填码、不直接授予权益。
- 发送失败、请求过于频繁、账号已有有效权益和兑换失败均显示可操作但不泄露内部信息的提示。
- 简体中文、繁体中文和英文界面及邮件文案同步提供。

## 资格与续期规则

- 申领资格由服务端当前时间和 Entitlement.expiresAt 判定，不信任客户端按钮状态。
- 没有 Entitlement，或 expiresAt 小于等于当前时间，视为可申领。
- expiresAt 晚于当前时间时，不可申领自助码，也不可兑换已经发出的自助码。
- 每次成功兑换从兑换时刻开始新的 31 天权益窗口。
- 过期后重新激活时，AI Credits 按现有规则重置为限额 20、已用 0。
- 自助码不能提前续期、累计未来天数或叠加 AI Credits。
- 管理员通用码继续按现有规则从“当前时间或现有到期时间中的较晚者”延长权益，并保留其现有配额语义。

## 自助码规则

- 自助码来源标记为 self_service_email，并绑定申请用户 ID。
- 自助码只在 SMTP 接受邮件后变为可兑换状态。
- 同一账号最多保留一个可兑换的自助码；新的自助码成功启用时，旧的未兑换自助码失效。
- 发送失败或服务端在启用前中断时，待投递码不可兑换。
- 自助码明文只存在于一次请求的服务进程内存和发出的邮件中；数据库、日志和 API 响应只保留 hash、短前缀及状态元数据。
- 自助码沿用现有默认 30 天兑换截止时间。用户在截止后仍未兑换，可以在符合限流和未授权条件时重新申领。
- 账号不匹配、码已失效、码已兑换或码已过期时，兑换接口返回统一的无效激活码错误。

## 限流与可用性

- 申领接口必须要求有效桌面会话，收件邮箱从会话对应用户读取，请求不得提交任意收件邮箱。
- 自助激活邮件复用数据库持久化的邮件发送限流边界：
  - 同一邮箱每 60 秒最多一次发送尝试；
  - 同一邮箱每个固定小时最多五次发送尝试；
  - 同一可信客户端 IP 每个固定小时最多二十次发送尝试。
- SMTP 失败仍计入限流，避免失败补偿造成并发绕过或邮件风暴。
- 限流响应提供可安全展示的重试时间；客户端在成功响应后按该时间禁用按钮。
- 服务端保留自助发码功能开关，用于分阶段发布和紧急止损。关闭时账号状态不声明申领能力，桌面端不显示按钮。

## 安全与隐私

- 自助激活码是账号绑定的单次 bearer secret；即使邮件被转发，也不能由其他账号兑换。
- 激活码兑换、账号绑定校验、有效权益校验、码消费和权益写入必须在同一 Store 事务中完成。
- 日志不得包含激活码明文、邮件正文、Authorization/Cookie、邮箱完整正文、会话令牌、LLM key 或数据库原始错误。
- 自助申领不上传或读取视频、音频、文字稿、洞察、模型缓存、本地历史、文件路径或用户本地配置。
- 服务端只通过现有 HTTPS 桌面 API 和既有 SMTP 配置处理账号、授权码、权益与配额元数据。

## 非目标

- 不改成点击按钮后直接授权。
- 不自动兑换邮件中的激活码。
- 不启用微信支付、订阅扣款、发票、退款或付费套餐。
- 不移除管理员通用激活码或管理员补偿能力。
- 不在本次设计中增加 Web Dashboard 的申领或兑换入口。
- 不增加邮件收件箱读取、邮件链接一键登录或新的身份认证方式。
- 不修改 worker、ASR、视频处理、InsightFlow 或本地产物边界。

## 验收标准

- 未登录、有效授权、未授权和授权过期四种账号状态下，申领按钮可见性符合本规格。
- 未授权账号成功请求后，服务端只向该账号邮箱发送一个可兑换的绑定码，API 不返回明文。
- 其他账号兑换该码失败，申请账号兑换成功后获得从当前时间开始的 31 天权益和 20 次 AI Credits。
- 有效权益账号无法通过 UI、直接 API、旧自助码或并发请求叠加授权。
- 权益过期后，同一账号可以再次完成“申领邮件码 → 手动兑换”，次数不设总量上限。
- 重复申领成功启用新码后，旧自助码不可再兑换。
- SMTP 失败、进程在码启用前中断或数据库提交失败不会留下可兑换的孤儿码。
- 并发申领至多产生一个成功发送结果，并发兑换至多消费一次、授予一个权益窗口。
- 管理员通用码创建、展示和兑换行为保持回归兼容。
- 新旧数据库迁移、三语言文案、Server/App/Rust 测试和文档治理门禁通过。
