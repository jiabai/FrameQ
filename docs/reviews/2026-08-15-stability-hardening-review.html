2. 加固建议（按优先级）

🔴 高优先级

#问题与证据影响建议修复
H1 ONNX 缓存残留目录无清理：_download_onnx_model_cache 的 .onnx-staging-<uuid> 与 _promote_onnx_cache 的 .onnx-backup-<uuid> 在 watchdog 杀进程 / 断电时残留（每份约 500MB 模型文件）；_remove_stale_temp_dirs 只清理 modelscope 的 ._____temp 多次中断下载后磁盘静默泄漏，可能最终导致磁盘满 下载开始前（或 normalize 阶段）清理 onnx-staging-* / onnx-backup-* 残留；加对应单测
H2 自定义归档下载通道无超时/重试/进度：_resolve_archive 使用 urllib.request.urlretrieve（无 timeout 参数、无进度回调、无断点），一旦 .env 配置自定义下载源，连接挂起时只能等 watchdog 10 分钟 自定义源场景（如镜像/内网分发）稳定性差，UI 无进度 复用 download_reliability.py 的流式下载（timeout / stall 检测 / max_bytes / content-type 校验）+ 进度事件；或 requests 流式 + 显式超时
H3 下载前无磁盘空间预检：SenseVoiceSmall 全套约 1.5GB+，磁盘不足时下载到一半才 ENOSPC 失败（已有分类但为时已晚） 磁盘满用户白等一次大下载 下载前检查 app-local 分区可用空间 ≥ 阈值（如 2GB），不足返回明确提示；Rust 或 Python 侧均可
H4 VC++ 预检只覆盖下载命令：check_vc_runtime 仅在 download_asr_model 前执行；视频转写等其它 worker 操作在 DLL 缺失时仍会 import 崩溃并显示笼统失败 同类问题在转写路径复发时不可诊断 把预检下沉到统一 worker spawn 入口（WorkerLane::run 或 spawn_worker_process），或至少让其它操作失败时也能看到 runtime 提示

🟡 中优先级

#问题与证据建议修复
M1 PyTorch 版缓存校验只查文件存在：validate_asr_model_cache 对 model.pt 无大小/哈希校验，截断文件可能被当作成功（ONNX 版已有全套 SHA256） 对 model.pt / vad model.pt 增加最小大小校验（或抽样哈希）；与 ONNX 版校验强度对齐
M2 依赖版本漂移：pyproject 中 modelscope>=1.37.1、torch>=2.10.0 为下限浮动，不同时间打包解析不同版本；ONNX 资产哈希针对固定文件，但 SDK 行为可能随版本变化 锁定精确版本（或提交 uv lockfile），使 CI 打包可复现；发布时记录实际解析版本
M3 桌面日志无轮转：frameq-desktop.log 无限 append（ASR 诊断日志有 4MiB 上限，desktop 日志没有） 加大小轮转（如 16MiB 滚动保留旧文件）
M4 发布 CI 门禁待确认：desktop-release.yml 仅见 build-installer 步骤，未见 pytest / cargo test / npm test 与 canonical↔packaged worker 字节对比门禁 确认测试门禁是否在其它 workflow；建议发布 CI 增加字节对比步骤（本批已手动验证一次，应固化）

🟢 低优先级

#问题说明
L1 下载进度事件无节流 modelscope chunk 级事件 → 大文件上千次 IPC/setState；可节流（≥100ms 或 ≥1% 增量）
L2 前端 45s stalled 提示与 10 分钟 watchdog 之间无操作 提示已存在，可在 stalled 持续 2 分钟时强化「可取消」引导
L3 app-local DLL 与系统 DLL 版本差异 msvcp140 向后兼容良好，风险低；不处理，但可在打包时记录 DLL 版本便于排障
